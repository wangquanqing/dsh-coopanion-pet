### 风险 1｜55「识别完填进输入框」——**可能拿不到那个能力**

- **已查清机制**（读了 `dsh-client-ui-conversation` 的源码）：`inputActions` 来自
  `ctx.uiSession.provide({ hooks: ['conversation','input'], props: ['inputActions'], resolve: ... })`——
  它**只注入给声明了该 props 的槽**，值是 `shell.actions`。
- 本插件占的是 `shell.overlay` 槽（root 作用域），**标准 props 是空接口**（README 里已实测记录）。
- **结论：本插件拿不到 `inputActions`。** 要走通 55，必须让桌宠也注册进
  `conversation.input.activity` 槽（或让宿主侧转发），不能靠现有插槽白拿。
- **三条备选**：
  ① **让桌宠也注册进 `conversation.input.activity` 槽**——能拿到 `inputActions`，但那是输入框旁边的
     活动区，视觉上要多放一份 UI；不过可以把 UI 做成几乎不可见（只在识别中显示一个小指示）。
  ② 用 DOM 直接找输入框并派发事件——脆弱，DSH 改版就坏，不推荐。
  ③ **改由宿主侧 `agent.followup`** 把识别文本作为一条用户消息发出——语义变成「用户说了这句话」，
     会直接触发一轮对话（而不是填进输入框等用户自己按回车）。语义略不同但实现最稳。
- **推荐 ①**（能真正「填进输入框」，体验最对），把 ③ 作为降级方案。
- **动手前先验**：在 `conversation.input.activity` 槽注册一个测试组件，确认 `inputActions.insertText` 可用。

### 风险 2｜54「假流式」——**识别质量可能不可接受**

- DSH 的识别接口收**整段 WAV**。分片送（如每 2 秒）意味着每片都被当**独立音频**识别。
- SenseVoice 对过短音频（<1 秒）可能识别为空或乱码；拼接结果可能比整段识别差很多。
- **先验**：录 3 秒的话，切成 3 片各 1 秒分别识别，看拼起来是否可读。

### 风险 3｜41「沙箱 frame」——**沙箱形态要验**

- 上游用 `web/figure-frame.html` 在一个**opaque origin**（无网络访问）里跑形象包代码，靠 `postMessage` 通信。
- DSH 插件能否创建这种沙箱 iframe？`sandbox` 属性 + `srcdoc`/blob URL 理论上可以，
  但**插件资源路由是同源的**，形象包要加载纹理就得能访问 `/api/dsh-coopanion-pet/assets/`——
  而 opaque origin 拿不到同源资源。
- **这意味着 41 的沙箱形态需要重新设计**：可能得放弃「opaque origin」，
  改用「同源 iframe + 严格的代码审查」（安全性下降），或者「宿主侧预解析清单 + 客户端只加载纹理」。
- **先验**：探沙箱 iframe 能否加载插件资源路由。

## 六、后续问题：「与客户端平级的前门」——**已决策：不做**

**问题**：桌宠能否做成与 `dsh-web-app` / `dsh-tui` 平级的前门，而不是它们的插件？

**结论**：技术上成立，但**决定不做**（2026-10-18 用户拍板）。

**技术事实**（已实测，详见 `tui-research.md`）：

| | dsh-web-app | dsh-tui |
| --- | --- | --- |
| `dsh.client.platform` | `"web"`（浏览器渲染） | **无 `client` 字段**（宿主侧 Ink 渲染终端） |
| 界面位置 | 浏览器 | Node 进程 |

- `dsh-tui` 之所以「不依赖浏览器」，是因为它**放弃图形形象、改用字符画**
- 本插件 `client.platform: "web"` 绑死浏览器；去掉它就得换一套表现层
- 三条路：**A** 换 Ink（字符画的她）/ **B** 引入 Electron 做原生窗口（保留真形象，
  但做不到透明/穿透/置顶）/ **C** 什么都不做（工具已在宿主侧，装进任何 profile 都能用，
  只是看不见她）

**为什么不做**：桌宠的核心卖点是那个 WebGL 形象，而「不依赖浏览器」要么牺牲形象（A），
要么引入 Electron 并接受三条限制（B）。**两者不可兼得**，收益不抵代价。

**现状已足够**：12 个 `pet_*` 工具在宿主侧注册，与界面无关——装进 `dsh-tui` profile 后
工具全部可用，`pet_say` 如实回 `offline`（她不在屏幕上）。**这是正确行为，不是故障。**

**若将来重启此议题**：先读 `docs/tui-research.md`（含实测证据与三条硬约束），
并注意 `dsh-tui` 的 `companion` 侧栏**已内置鲸娘陪伴**（267 张 PNG 帧 + 22 动画，默认开启），
因此 A 路会与它重复。
