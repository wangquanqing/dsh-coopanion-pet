## 一、为什么现在的插件形态做不到

| 事实 | 证据 |
| --- | --- |
| **插件没有宿主就加载不了** | 客户端半边是 `window.__ModuleLoader__.load()` 注入的浏览器端 cordis 插件，由 DSH 的 Web 前端装配。DSH 没起来 → 没有页面 → 没有 loader → 她不存在 |
| **宿主半边是 DSH 进程内的一个 cordis 插件** | `index.js` 的 `apply(ctx)` 依赖 `ctx.inject(['webServer','tools','systemPrompt'])`。没有 DSH 进程就没有这些服务 |
| **本机没有可用的 Electron 运行时** | `~/.dsh/dsh-runtimes/` 下只有 `dsh-primary-runtime`（Node/pnpm/python），没有 Electron；npm 上的 `@deepseek-ai/dsh` 依赖里也没有 electron |
| **DSH 桌面端是独立安装的应用** | 装到 `~/AppData/Local/Programs/`（本机只找到 updater 的 `installer.exe`），是打包好的 Electron 应用；**它的 Electron 不对外暴露给插件** |
| **npm 包的形态限制不了启动时机** | 插件包本身没问题（它已经是 npm 包了），但「什么时候被加载」由 DSH 决定，插件自己说了不算 |

所以：**「开机就有桌宠」在纯插件形态下无解**——因为开机时 DSH 还没跑，插件没有宿主。

## 二、可行的三条路

### 路线 A：做一个独立的「桌宠壳」小应用（你的原始设想）

**做法**：新增一个独立的 Node 进程（可做成 npm 包，如 `dsh-coopanion-pet-standalone`）：

1. 它自己起一个极小的 HTTP 服务，serve 她的页面（复用现有的 `assets/`，**渲染内核与形象包完全不用改**）
2. 用 `msedge --app=<url>` 或（若以后有 Electron）开一个无边框窗口
3. 通过 Windows 启动文件夹或注册表实现开机自启
4. **基础能力**：走动、气泡、装扮、音效、位置记忆——这些全在客户端，不依赖 DSH
5. **DSH 起来后自动升级**：它去轮询/连接 DSH 插件的 SSE（`/api/dsh-coopanion-pet/events`）。连上之后，状态气泡、`pet_*` 工具、语音、CUA 审批**自动全部可用**——因为那条通道本来就是插件提供的

**为什么这条路的接缝是现成的**：本插件的宿主↔页面通道（SSE 下行 + POST 上行）**本来就是 HTTP**，
不是 DSH 的私有 RPC。独立壳只要把同样的 URL 连上，功能就接上了。这是当初选 HTTP 而不是 RPC 的意外收益。

**代价与局限（必须如实说）**：

| 项 | 情况 |
| --- | --- |
| 工作量 | 新增一个宿主半边，估 **300–500 行**（HTTP serve + 窗口拉起 + 自启管理 + 与 DSH 的连接状态机） |
| **窗口透明** | **做不到全透明**。`msedge --app` 开的是普通窗口，不能设置「透明 + 鼠标穿透」。只能近黑背景的边框窗口。**这是最大的体验损失** |
| 鼠标穿透 | 独立窗口里做不到「点空白处穿透到桌面」——那是 Electron 窗口级能力。她自己的界面元素仍可点 |
| 置顶 | `--app` 窗口默认不置顶；需要额外手段（AutoHotkey / PowerShell SetWindowPos）才能置顶，且不一定稳定 |
| 开机自启 | Windows 启动文件夹放一个 .lnk 即可（**可行**）；或注册表 Run 键 |
| 两套进程的关系 | 独立壳与 DSH 插件**同时存在**时，会出现**两个她**（一个在独立窗口、一个在 DSH 页面里）。需要做成「检测到 DSH 页面已连上就自动收起独立窗口」，否则体验混乱 |
| 端口/单例 | 需要处理「DSH 没开」「DSH 开了」「DSH 关了」三种状态与重连 |
| 打包分发 | 从「一个 npm 包」变成「npm 包 + 一个要开机自启的进程」，安装/卸载都更复杂 |

### 路线 B：只用 DSH 桌面端的启动配置（最省事，但达不到你的原始目标）

如果 DSH 桌面端支持「开机自启」+「启动时加载某 profile」，那么「开机后自动有桌宠」能达成——
**但她不会在 DSH 起来之前出现**，中间有几秒到几十秒的空窗。

我探到的事实：本机 DSH 桌面端是打包应用，**我没有找到它对外的开机自启配置项**（需要查它的设置界面或配置文件才能确认）。
这条路的验证成本低，但**不满足你「DSH 没起来时也有基础能力」的要求**。

### 路线 C：不做独立应用，只做「启动方式」设置项

保持纯插件，只加设置项：随 DSH 桌面端启动 / 随网页打开启动。
**这是伪选项**——插件没法自己决定何时被加载，这个设置项实际上没有落点。

## 三、路线 A 的技术验证清单（动手前该先验的）

如果要做路线 A，**先验这五件事**，任何一件不通过都要重新评估：

| # | 要验什么 | 怎么验 | 不通过的后果 |
| --- | --- | --- | --- |
| 1 | `msedge --app` 能否稳定开一个无地址栏的窗口，并指定尺寸/位置 | 起一次命令看效果 | 窗口形态不可控，要改用别的壳 |
| 2 | 该窗口能否置顶（PowerShell `SetWindowPos` / AutoHotkey） | 写个小脚本试 | 她会被其他窗口盖住 |
| 3 | 透明背景是否真的做不到（或有没有别的办法） | 试 `--app` + 页面背景透明 | 只能接受近黑背景 |
| 4 | 独立壳能否连上 DSH 插件的 SSE，并让工具/状态气泡真的生效 | 起独立壳 + 起 DSH，看状态气泡 | 接缝不成立，整套设想作废 |
| 5 | 两套进程共存时怎么避免「两个她」 | 设计单例与优先级 | 体验混乱 |

**其中第 4 条是关键**：它决定「DSH 起来后接完整能力」这句话是否成立。
我判断**大概率成立**（通道本来就是 HTTP），但没实测过，不能算数。

## 四、我的建议

1. **如果你要的是「开机就有她、且她能在桌面上自由站立」** → 路线 A 是唯一解，但要接受
   **不透明、不穿透、可能盖不住**这三项损失。做之前先验第三节那五条。
2. **如果你要的是「DSH 一开就有她」** → 路线 B 或干脆不改：DSH 桌面端若支持开机自启，她就跟着来。
3. **纯插件形态下，本文档第一节那五项（31/32/33/39）仍然拿不到**——这与独立壳是两件事：
   独立壳能给她**一个窗口**，但给不了**透明/穿透/托盘/全局热键**（那些仍需 Electron 主进程）。

**换句话说**：路线 A 解决的是「她在 DSH 之外也能存在」，
**不解决**「她像原生应用那样透明浮在桌面上」——后者除非 DSH 桌面端把 Electron 能力开放给插件，
否则无论怎么包装都做不到。
